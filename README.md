# Мебельное производство - ЛР №3

Учебная реализация согласованной части курсового проекта. Разработка и запуск на Mac с Apple Silicon.

## Что реализовано

- `Furniture.Employees`, порт 5101: создание учетной записи сотрудника, список, карточка и изменение контактных сведений. Роли - набор значений `EmployeeRole`. Пароли хранятся как хеши и не возвращаются в ответах.
- `Furniture.Orders`, порт 5102: создание, просмотр и изменение клиентов; создание заказа, список и карточка заказа с первым этапом, назначениями и историей.
- `Furniture.Summary`, порт 5103: список заказов с именами ответственных администраторов и количество заказов по каждому статусу. Данные получает по HTTP от других сервисов.
- `Furniture.Shared` - библиотека транспортных моделей и общих настроек. Это не четвертый сервис; собственного процесса и базы у нее нет.

У сервиса сотрудников база `furniture_employees`, у заказов - `furniture_orders`. Сводный сервис не обращается к чужим таблицам и не имеет собственной базы. Идентификаторы сотрудников в заказах и назначениях проверяются через API; внешних ключей между базами нет. Общая предметная модель сохраняется.

## Сценарий создания заказа

1. Администратор авторизуется, выбирает существующего клиента и передает адрес, описание, пожелания и плановый срок.
2. Система создает заказ в `New` и первый этап замера и согласования. Изделий при создании может не быть.
3. Из активных сотрудников с ролью `Measurer` выбирается свободный: без назначений `Assigned` или `Accepted`. При нескольких кандидатах выбирается дольше всех не получавший назначение; равенство разрешается по идентификатору.
4. Если замерщик найден, создается `EmployeeAssignment`, этап получает `Assigned`, заказ - `MeasurementAndApproval`. Назначение и смена статуса записываются в историю.
5. Если свободного замерщика нет, этап получает `WaitingForAssignee`, заказ сохраняет `New`, назначения нет.
6. Администратор получает номер, состояние заказа и результат назначения.

Выбор замерщика и запись назначения защищены транзакцией PostgreSQL и блокировкой на время транзакции: параллельные запросы не назначают одного свободного сотрудника дважды. Ошибка связи с сервисом сотрудников возвращает 503, а не изображает отсутствие свободных работников.

## Запуск на этом Mac

В Терминале перейти в папку проекта:

```bash
cd '/Users/optif1ne/Учеба/3 курс/5 семестр/ТП/ЛР 3/Microservices'
python3 scripts/dev.py start
```

Скрипт запускает отдельный локальный кластер PostgreSQL на `127.0.0.1:55432`, проверяет сборку и запускает три сервиса. Используются установленные бинарные файлы PostgreSQL 18 из `/Library/PostgreSQL/18/bin`. Системный кластер и его пароль не нужны. При первом запуске создаются две базы и отдельные пользователи для них; миграции применяются сервисами при запуске. В `.local/` сохраняются данные, журналы и сгенерированные пароли. Повторный запуск данные не удаляет.

Проверка и остановка:

```bash
python3 scripts/dev.py status
python3 scripts/dev.py stop
```

Локальный SDK находится в `.tools/dotnet`. Команды .NET вызываются через оболочку:

```bash
./scripts/dotnet.sh --info
./scripts/dotnet.sh build Furniture.slnx --no-restore --disable-build-servers -m:1 -p:UseSharedCompilation=false
```

Для переноса на другой Mac необходимо установить .NET SDK версии из `global.json`, PostgreSQL и восстановить NuGet-пакеты. Папки `.tools/` и `.local/` в исходный код не включаются. Если PostgreSQL установлен в другом месте, перед запуском указать `TP_PG_BIN` с путем к его `bin`.

```bash
./scripts/dotnet.sh restore Furniture.slnx
```

При необходимости создать следующую миграцию сначала установить локальное средство EF:

```bash
./scripts/dotnet.sh tool install dotnet-ef --version 10.0.14 --tool-path .tools/ef
./scripts/dotnet.sh ef migrations add НазваниеИзменения --project src/Furniture.Orders
```

## Проверка в Postman

1. Запустить сервисы.
2. Импортировать `postman/Furniture.postman_collection.json`.
3. Импортировать `.local/Furniture.local.postman_environment.json` и выбрать это окружение. Файл создается при запуске и содержит локальный пароль администратора; не включать его в публичный отчет или репозиторий.
4. Запустить коллекцию целиком по порядку. Она содержит 27 запросов с проверками ответов.
5. Для скриншотов отдельно открыть создание клиента, создание замерщика, оба результата создания заказа, карточку, сводный список и статистику. Скрыть панель авторизации и пароль окружения.

Коллекция использует Basic Auth. Начальный логин - `admin`; пароль сгенерирован в локальном окружении. Изменять его вручную в environment без изменения учетной записи не следует. Для этой локальной демонстрации сервисы слушают только loopback и используют HTTP; перед внешним размещением потребуется HTTPS.

Автоматический прогон выполнен через Newman 6.2.3, средство запуска коллекций Postman. Подтверждение без секретов: `verification/postman-results.json` (27 запросов, 47 успешных проверок). Это не скриншоты настольного Postman; изображения для отчета нужно сделать при демонстрации по шагу 5.

Первый запуск коллекции рассчитан на первоначальную базу с одним администратором. После полного успешного прогона все созданные замерщики заняты, поэтому повторный прогон также проходит. Если самостоятельно добавить свободных замерщиков или прервать коллекцию посередине, проверки ветки ожидания могут потребовать подготовки данных. Пустой пример окружения без секретов находится в `postman/Furniture.example.postman_environment.json`.

Дополнительная проверка параллельных запросов, отказа сервиса и сохранения данных:

```bash
python3 scripts/check_scenarios.py
```

Она добавляет демонстрационные записи и кратковременно перезапускает только сервис заказов. Запускать после полного прогона Postman-коллекции, когда прежние замерщики уже заняты.

## Основные адреса

| Сервис | Метод и путь | Действие |
|---|---|---|
| Сотрудники | `GET /api/auth/me` | Проверить вход, получить текущего сотрудника |
| Сотрудники | `GET /api/employees` | Список сотрудников |
| Сотрудники | `GET /api/employees/{id}` | Карточка сотрудника |
| Сотрудники | `POST /api/employees` | Создать учетную запись с ролями |
| Сотрудники | `PUT /api/employees/{id}` | Изменить ФИО и телефон |
| Заказы | `GET /api/clients`, `GET /api/clients/{id}` | Получить клиентов |
| Заказы | `POST /api/clients`, `PUT /api/clients/{id}` | Добавить или изменить клиента |
| Заказы | `POST /api/orders` | Создать заказ и попытаться назначить замерщика |
| Заказы | `GET /api/orders`, `GET /api/orders/{id}` | Список и карточка заказов |
| Сводные данные | `GET /api/summary/orders` | Заказы с именами администраторов |
| Сводные данные | `GET /api/summary/statistics` | Количество заказов по статусам |
| Каждый сервис | `GET /health` | Проверить, запущен ли процесс |

`/health` проверяет процесс, а не готовность всех зависимостей. Все перечисленные предметные операции первой версии доступны администратору. `/api/auth/me` доступен любому активному сотруднику с правильным паролем. Доступ исполнителей к их назначениям относится к следующему этапу реализации.

## Что объяснить на защите

- Модель - класс с данными, например `Employee` или `Order`.
- Контроллер получает HTTP-запрос, проверяет данные, выполняет действие и возвращает HTTP-ответ с JSON.
- `DbContext` связывает C#-объекты с таблицами PostgreSQL.
- Code First означает, что структура таблиц создается миграциями на основе классов. Исходные миграции лежат в папках `Migrations` обоих сервисов.
- `POST` создает данные, `GET` читает, `PUT` изменяет. В согласованный объем этой версии удаление не входит.
- Композитный сервис объединяет ответы независимых сервисов. Он не подключается напрямую к их базам.
- `201` означает создание, `200` - успешное чтение или изменение, `400` - неверные данные, `401` - нет корректного входа, `403` - нет прав, `404` - запись не найдена, `409` - занятый логин, `503` - зависимый сервис недоступен.

## Границы этой версии

Не реализованы изменение ролей существующего сотрудника, отключение учетной записи, последующая обработка очереди, замеры и изделия, полный цикл производства, доставка, сборка, платежи, подзаказы и веб-интерфейс. Требования к ним остаются в общей спецификации. Изделия пока не создаются ни отдельным endpoint, ни фиктивными строками. `AgreedCost` первоначально равна нулю и в этой версии не означает согласованной стоимости.

В диаграмме классов пока остается прежняя кратность `1..*` у изделий заказа. В спецификации согласовано `0..*`; напоминание исправить рисунок при следующей лабораторной или этапе курсового находится в корневом `AGENTS.md`.

## Версии

В этой сборке: .NET SDK 10.0.403, ASP.NET Core 10.0.14, EF Core 10.0.14, Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3, PostgreSQL 18.4. Пакеты EF и провайдера совместимы; номера исправлений у разных поставщиков не обязаны совпадать.
